## Summary

Add the durable, store-neutral read-cursor persistence foundation for conversation unread synchronization. One monotonic high-water mark is stored for each world, reader, and conversation across in-memory, file, and SQLite backends.

Refs #4173

## Changes

- Add typed reader identity and opaque non-negative read position value objects.
- Define one read-state contract whose ordinary advance operation retains the greatest submitted position and changes version only for a real advance.
- Add in-memory atomic updates, file-backed atomic replacement with per-key cross-process locking, and SQLite conditional upsert with a composite primary key.
- Reject uninitialized typed identities consistently before persistence.
- Add shared contract coverage for key isolation, delayed lower writes, idempotent retries, concurrent updates, durable reopen, and one-record-per-key storage.

## Anti-reinvention

The change follows the repository's existing Vogen identifier conventions, SQLite connection factory, targeted SQLite pool cleanup, and memory/file/SQLite store parity pattern. Source review covered the three conversation stores, existing conversation identity types, world scoping, PR #4170's merged stable entry identity, and open PR overlap. A separate read-state store is necessary because the current conversation aggregate has no per-reader state and ordinary aggregate saves must not clobber independently advancing cursors.

## Risk & rollback

- Blast radius is additive: no runtime service registers these stores yet, so existing conversation, REST, SignalR, and portal behavior is unchanged. File-store locking depends on filesystem exclusive-open semantics; SQLite uses database-level conditional upsert semantics.
- Roll back the single commit to remove the foundation. No existing schema or persisted conversation row is modified until a later runtime composition slice registers a chosen implementation.
- Tests are additive. No assertion, skip, timeout, threshold, or baseline was weakened to obtain green.

## Merge notes

This is an independently reviewable foundation slice and intentionally does not close #4173. Remaining scope includes runtime store composition; server-owned claims/local-reader identity; authorization; stable append-position derivation and unread visibility/count queries; REST summary/advance operations; user-scoped SignalR fan-out; desktop/mobile visibility and scroll-aware acknowledgement; reconnect reconciliation; documentation; and browser/multi-connection coverage. Those layers should consume this monotonic persistence contract rather than duplicate storage semantics.

The change adds new types, store implementations, and a SQLite table created lazily by the new SQLite store. It does not migrate existing databases, register services, alter APIs, or change UI. Passing validation does not authorize merge.
