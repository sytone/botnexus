## Summary

`LegacyConversationResolver` services a one-time backfill (#615) that closed 2026-05-29, yet it is still an always-on component on the session load and save paths. It cannot be deleted today because **nothing can prove whether it is still being reached**: all three session stores construct it with `logger: null`, so every activation is silent. This PR closes that observability gap and documents the standing convention that should have retired the shim months ago.

Closes #2311

## Changes

- **New `LegacyConversationTelemetry`** (`BotNexus.Gateway.Sessions`) — process-wide, allocation-free activation counters for the legacy shim. Records resolves, creates, and binds, and exposes a `Snapshot()` whose `HasActivity` flag directly answers the deletion question. Static by design: the resolver sits on hot session paths and is constructed directly by three stores, so instrumentation must not add per-call allocation or a threaded dependency.
- **Attributed every resolver call site** via a new `LegacyResolveReason` parameter, so activity is diagnosable rather than just countable. `StartupMigration` is the eager sweep working as intended; `LoadTimeBackfill` or `SaveTimeStamp` activity means unmigrated data is *still arriving* and the shim is genuinely load-bearing. Un-attributed callers land in `Unspecified` so the total is never under-reported.
- **Escalated legacy-conversation creation from `Information` to `Warning`.** Minting a new `legacy:{agentId}` row months after #615 closed is an anomaly, not routine, and the message now names #2311 so an operator can act on it.
- **New `docs/development/compat-shim-lifecycle.md`** — the migrate-forward-then-delete convention (issue part 5), with checklists for introducing and removing a compat shim. Linked from `docs/development/README.md`.

## Scope judgement — what shipped and what did not

Shipped **(a) audit telemetry** and **(e) the convention doc**.

- **(b) eager forward migration — already in the repo, no work needed.** `SqliteSessionStore.MigrateOrphanedSessionsAsync` and `FileSessionStore.MigrateOrphanedSessionsAsync` already perform an idempotent one-shot sweep per process. The resolver's remaining load/save call sites are defensive fallbacks, not the primary migration mechanism.
- **(c) deletion — deliberately NOT done; it cannot be proven safe from the repo alone.** Three reachable non-startup call sites remain (`FileSessionStore.LoadFromFileAsync`, and `EnsureConversationIdStampedAsync` in the SQLite/File/InMemory stores), so this is not dead code by inspection. Whether they *fire* depends on data in live environments, which the source tree cannot answer — and until this PR, neither could a running gateway. That is precisely the audit gate the issue asks for. **Deletion should be a follow-up PR once `LegacyConversationTelemetry.Snapshot().HasActivity` is confirmed false in a real environment.**
- **(4) repo-wide compat-shim sweep — out of scope**, per the issue's own sequencing and to keep this reviewable. Follow-up.

## Anti-reinvention

- **Reuses the single conversation-creation seam** from #2310 / PR #2321 — `ConversationFactory.CreateForChannel` is left exactly as PR #2308 stamped it. **No new creation site added.**
- **No new metrics abstraction invented.** The repo has no `System.Diagnostics.Metrics.Meter` infrastructure (searched `new Meter(` across `src/` — zero hits), so a purpose-built counter type matching the existing `ActivitySource` + `ILogger` style was the minimal fit. It is documented as intentionally short-lived and deleted alongside the resolver.
- **No overlap with open PR #2328** (`refactor/2305`, deletes virtual-session inference) — verified via `gh pr diff 2328 --name-only`; it touches the Blazor client, domain `Conversation.cs`, and provenance docs, and does not modify any session store.
- **Existing eager migrations reused, not duplicated** — no second sweep added.
