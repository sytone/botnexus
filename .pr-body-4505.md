## Summary

Compose extension repository clone, build, and deployment into one serialized reconciler and invoke it from build, update, serve, gateway start/restart, CLI sync, and the Portal Sync Now action. Repository failures remain named and non-fatal to platform update/startup while existing staged and live output stays available.

Closes #3904

## Changes

- Add one cross-process `ExtensionLifecycleReconciler` that reads enabled registrations, clones/updates repositories, builds complete candidate generations, and runs the existing deployment reconciliation once.
- Move the existing clone, project-build, and hardened deployment primitives into the shared configuration assembly so both CLI and gateway API hosts use the same pipeline.
- Invoke reconciliation only after successful BotNexus builds in build/update/serve/gateway lifecycle paths; repository failures are reported without preventing update restart or host availability.
- Add `extension repository sync` (with the existing `reconcile` alias) and wire Portal Sync Now through the same authenticated API operation.
- Preserve no-registration behavior: host startup still refreshes in-tree deployment, while repository-maintenance commands perform no deployment work when the registry is empty.
- Serialize overlapping CLI/API invocations with a home-scoped process and file lock.

## Anti-reinvention

The implementation composes `ExtensionRepositoryRegistryService`, `ExtensionRepositoryCloneReconciler`, `ExtensionProjectBuildService`, and `ExtensionDeploymentReconciler`. Current source and open pull requests were checked; no open PR owns #3904. The only new production abstraction is the missing coordinator that makes those existing primitives share one ordering, lock, failure-isolation, and result contract.
